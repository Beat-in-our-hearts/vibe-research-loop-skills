# Plan an experiment

An experiment is one controlled comparison: a baseline, a treatment that changes exactly one thing, and ablations when needed. Plan it so that a reviewer can follow it without this conversation.

1. **Idea.** Take the idea the user names, or else query Ideas and take the highest-Priority approved idea in Backlog. Go on only if its Human Approved is checked; otherwise tell the user and stop. Read its Planned test, Stages and budget, and earlier experiments, and decide:
   - Stage: the one the latest experiment's Conclusion proposes, or else the earliest stage not yet run whose previous stage's Go on when holds.
   - Budget left: each limit minus what the idea's earlier experiments used: their number, the days to the Deadline, and their single-GPU hours, from the GPU hours row of each finished experiment plus, for one still running, `gpu_hours.py` on its log folder on each machine that runs it. If `gpu_hours.py` exits 3, show the user what it could not count, and stop.
   - Plan the whole stage if it fits the budget left; otherwise only the part that fits, such as fewer seeds, fewer controls, or shorter training, with each cut and its reason under Deviations. If not even its smallest useful part fits, tell the user the budget is used up and stop.
2. **Facts.** Before designing anything, settle every fact the plan rests on, read-only:
   - Take every number from a source you can point to, such as a log or results file, with the hardware it was measured on; mark anything nobody measured as an estimate.
   - Read the current machine in `docs/AGENTS/machine.md`, and check the code, environments, checkpoints, and data the plan needs; what is missing or must be rebuilt is setup work.
   - Read the code the plan builds on: never infer from a name what a hyperparameter does, or which inputs and targets a component takes from a sample.
   - Trace one training batch from the data loader to the total loss, with all that the template's Data flow and losses asks for.
3. **Page.** Create the page in Experiments with Name (the experiment in a few words: at most 15 words, or 20 characters in Chinese), ID (lowercase English words joined by hyphens, at most 24 characters, unique in Experiments, never renamed), and Idea. If the idea's Status is Backlog, set it to Testing.
4. **Draft.** Fill the Review callout, then sections 1 and 2, by the template's instructions. Step times count what the treatment adds over the baseline, re-evaluations, and environments to rebuild.
5. **Setup.** Do the setup steps of section 1 in order: the code and one config per run, by the workspace's git rules; then the environments and data; then the plan file, as step 6 describes; last, a short smoke run of each block's command, unchanged but for overrides that shorten it, with `launch_run.sh` in its free form: `--purpose '<date>-<name> / smoke <run>' --log logs/<date>-<name>/smoke-<run>.log --outputs tmp/smoke/<date>-<name>/<run>/ --code <checkout> --gpus <ids from the free: line> --machine <Name> --tmux <session> --wait <seconds> -- '<command>'`. If a step's condition to go on fails, stop and report.
   - Each checkout's `launch_run.sh --pin <checkout>`, run where the code runs, must print the same before and after its smoke run. A file the run writes into its checkout, such as `wandb/`, `outputs/`, or `lightning_logs/`, changes the pin, which stops the next launch: send it to `$VRL_OUTPUTS`, or ignore it in the checkout's committed `.gitignore`, and smoke-run again.
   - In remote mode, first show the user the page link and the writes these steps make on the remote host, the syncs included, and make only those they approve. Keep `--wait` below the command limit minus 20 seconds, and read a longer smoke run's footer later.
6. **Update.** As the template says, replace the planned values from the config snapshots, and the times from the smoke run's measured step times and the bottleneck it shows; set Est. Hours to the new wall-clock from the first run to the end of the plan. Bring `docs/plans/<date>-<name>.md` up to date, where `<date>` is the page's Created date and `<name>` its ID: a link to the page, then for each run its config file and one fenced block whose info string is `bash run=<run> gpus=<count> env=<environment>`, holding its exact launch command. Run names hold only letters, digits, `.`, `-`, and `_`; a seed run as its own process is a run with its own block, such as `baseline-s1`. The command enters its checkout and activates its environment itself, as in `cd main_repo && . .venv/bin/activate && python train.py --config configs/baseline.yaml --out "$VRL_OUTPUTS"`, writes its outputs to `$VRL_OUTPUTS`, and holds no token: a tool that needs a login uses the user's own, such as `hf auth login`.
7. **Self-review.** Read the page back as the user would, and revise it until every answer is yes:
   - Can a reader tell how many runs there are, what each does, and why each control is there, and follow one batch from the data to the total loss: every shape, where gradients stop, and every loss term with its weight?
   - Is every term, hyperparameter, and number explained in plain words and traced to its source, does the Basis separate measured from estimated numbers, and do the step times and the Total fit the current machine?
   - Does every deviation have a reason, every step a condition to go on and its writes, and is Decided by quoted unchanged?
   - Does the plan file hold one block per run of section 1, each the command its smoke run ran, with its GPU count and no `CUDA_VISIBLE_DEVICES` or token, and did each smoke run leave its checkout's pin unchanged?
   - Is each fact stated once, referring to the idea instead of repeating it, and does the Hyperparameters line say which config keys differ across runs?
8. **Report.** Pin each block: add to its info string what `launch_run.sh --pin <checkout>` prints, `code=<checkout>@<commit> diff=<...>` or `code=none`; in remote mode, take it from the line `vrl_ssh.sh sync` prints for the checkout. Make the plan file writable by you only with `chmod go-w`, since `launch_run.sh` refuses a plan others may change, then record its SHA-256, from `sha256sum` or `shasum -a 256`, after its name in the Code row of section 2. In remote mode, instead commit the plan file, sync `.`, and record the hash the sync prints for it; the mirror's copy is already writable by you only. Whenever the plan file, the code, or a config changes before approval, pin and record again, and name the change on the callout's Changed line. Rewrite the Review callout in place for the plan, show the user the page link and the callout's text, and ask them to review sections 1 and 2, by coloring text as the rules below describe or in words, and to tick Human Approved; launch nothing before they do.

## Rules

- At the start, run `bash <this skill's folder>/../vrl-init-workspace/scripts/check_update.sh`. If it reports a newer release, tell the user once per session, with its update command, and go on; update the skills only when asked.
- Work from the root of a vibe-research-loop workspace, which holds `AGENTS.md` and `docs/AGENTS/`, and follow its rules; elsewhere, tell the user and stop.
- If `docs/AGENTS/remote.md` exists, follow it: edit code, plans, and tests here and send them only as commits with `vrl_ssh.sh sync`, recording the pins and plan hashes it prints. Read logs and results with `vrl_ssh.sh read`, `run`, or `launch_run.sh --status`, and bring back with `vrl_ssh.sh fetch` only a figure to upload or a lock file to commit. Write plotting and analysis scripts on the remote host. Run no code here, not even a quick check.
- Never improvise what the scripts in `<this skill's folder>/../vrl-init-workspace/scripts/` do: `launch_run.sh` starts every long-running command, `resources.sh` reports resources and free GPUs, `gpu_hours.py` counts GPU hours, `vrl_ssh.sh` reaches the remote host. Read a script's `--help` only when you need an option that this skill or a rule file does not give. If one refuses or cannot count something (exit code 3), tell the user why; work around it by hand only where a rule file says how.
- If `docs/AGENTS/feishu.md` exists, the memory store is Feishu, not Notion: follow that file instead wherever this skill names Notion, `ntn`, a page, a database, or a property, and wherever a rule below makes sense only in Notion.
- Use the `ntn` CLI for Notion and look up its usage live: `ntn --help`, `ntn api ls`, `ntn api <path> -X <method> --spec`. Always run `ntn api ... < /dev/null`, or it waits on stdin.
- Take the IDs of the project page and databases from `docs/notion/ids.md`. If it is missing, find them by exact title with `ntn api v1/search`, reading every page of results, ask the user which project if several match, and record them there with the columns Object, Title in Notion, Page ID, Database ID, and Data source ID.
- Create each new page from its database's template file, never from a Notion template: `ideas.md`, `experiments.md`, `findings.md`, or `papers.md` in `<this skill's folder>/../vrl-init-workspace/references/guide/notion_guide/templates/`. Set the default properties from the file's header, and write each part of the body only when you fill it, at its place, by its italic instructions. A page holds only content: no instruction text, no `…` placeholder. Whenever an Ideas, Experiments, or Findings page goes to the user for review, rewrite its opening callout in place as its template says.
- A page whose headings differ from its template's comes from an older template: find each section by name, not number, and tell the user before writing to it.
- Write pages, template headings, labels, and table headers included, in the language the workspace's language rules set for them, or else the reply language, with property names and select and status options exactly as the database defines them.
- Write sentences a colleague can follow without decoding. State each fact once, where it belongs, and elsewhere point to its page and section, unless a template asks to repeat it. Give a reason only for a deviation, a control, an estimate, a ✘, or where a template asks. Common abbreviations such as w/o, ckpt, or lr are fine, but never string abbreviations and symbols together without words. Spell out at first use only those uncommon in the field or made up for this project.
- Keep each table cell to a value, a phrase, or one sentence. Put a cell's several points on separate lines within it (a `\n` in its rich text, since a cell cannot hold list blocks), starting with `1.`, `2.` when order matters and `•` otherwise. When a cell would run past three lines, move its content into a list right below the table, with a short pointer in the cell.
- The user marks text for review by coloring it or its background red, orange, or purple; other colors are not marks. Read a page before every write, with the colors of all its text, table cells included (each rich-text item's `annotations.color` and the block's `color`), and read it back after; merge the user's edits instead of overwriting them. Answer each mark, telling the user what you change and why. Red means wrong: fix it. Orange means not understood: explain it in plainer words and rewrite it so it needs no explanation. Purple means not acceptable: propose an alternative, and keep the text and mark until the user decides. Write rewritten text without the mark; leave unresolved marks in place.
- Add a figure by uploading its PNG with `ntn files create --filename <name>.png --content-type image/png < <file>` and inserting it as an image block right above its caption.
- Write times in the `TZ` of the workspace's `.env`: `YYYY-MM-DD HH:MM` in text, and `"time_zone": "<TZ>"` on date properties.
- Never make a Human-In-Loop decision: tick Human Approved, set Confirmed or Overturned, or change a Budget limit the user has set.
