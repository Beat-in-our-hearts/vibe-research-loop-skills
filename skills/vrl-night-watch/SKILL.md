# Night watch

While the user sleeps, keep the GPUs busy with work they approved. They start the watch before bed: in Claude Code, with `/loop /vrl-night-watch` and no interval, so that you time each wake-up; in Codex, from an automation that runs `$vrl-night-watch` every 30 minutes in the workspace itself, since a worktree has no `.env`, `logs/`, or `runs/`; elsewhere, from a scheduled job, such as cron, every half hour.

The window runs from 22:00 to 10:00 in the project's time zone, unless the command gives other hours, such as `/vrl-night-watch 23:00-08:00`. The only memory between wake-ups is `logs/<date>-night-watch.log`, where `<date>` is the window's last morning.

1. **Permissions.** When the user can read it, at the first wake-up of `/loop` or a run by hand before they set up an automation or a job, check that the watch can run unattended, and give them the exact rules it needs, for their own settings or `.claude/settings.local.json`, never a settings file the workspace repository shares. Recommend Claude Code's `dontAsk` mode, never one that skips every check. Use this machine's values: the scripts' path `S` and the GPU ids `I` from `docs/AGENTS/machine.md`, and in remote mode the alias `A`, the remote workspace `R`, and the command limit `L` from `docs/AGENTS/remote.md`. Call every script, `check_update.sh` included, as the rules write it: `bash S/<script>`, with `S` spelled out.
   - Allow:
     - `date`, and reads of `~/.agents/skills/` and `~/.claude/skills/`;
     - `bash S/check_update.sh`, and each script's `--help`;
     - `bash S/resources.sh --allowed I`, `python3 S/gpu_hours.py`, and `bash S/launch_run.sh --plan docs/plans/`; in remote mode, instead, `bash S/vrl_ssh.sh check A`, `bash S/vrl_ssh.sh connect A`, the read-only `bash S/vrl_ssh.sh read A --workspace R --limit L -- `, called without `--lines`, and `bash S/vrl_ssh.sh script A --workspace R --limit L -- ` followed by `resources.sh --allowed I`, `gpu_hours.py`, or `launch_run.sh --plan docs/plans/`;
     - the tmux session's start command and the quota command in `docs/AGENTS/machine.md`, exactly as written there; in remote mode, each as its whole line, `bash S/vrl_ssh.sh run A --workspace R --limit L -- '<command>'`, never as a `vrl_ssh.sh run` prefix, so that every other `run` call stays refused;
     - the memory store's page API: `ntn api v1/`, or `lark-cli base`, `lark-cli docs`, and `lark-cli wiki`;
     - edits of `logs/*-night-watch.log`, which stays local in remote mode.
   - Deny: `launch_run.sh` with `--resume` or `--new-session`; `ntn auth`, `ntn login`, `ntn logout`, `ntn files`, `ntn workers`, and `ntn update`; any `ntn api` call with the method `DELETE`, `in_trash` or `archived`, or data read from a file with `@`; any `lark-cli` call with `--yes`; edits of `docs/`, `.env`, `.claude/`, and the code folders; in remote mode, `vrl_ssh.sh sync` and `fetch`, and any local `python`, `python3`, `uv`, `pip`, or `pytest`, but not `vrl_ssh.sh run`, which would also refuse the two exact lines above.
   - In Codex, prefix rules match whole arguments and cannot deny an argument anywhere in a command: write them as `["bash", "S/launch_run.sh", "--plan"]` and so on, and tell the user that the denies hold there only as this skill's rules. The automation's sandbox also needs network access, for `ssh` and the memory store's CLI.
   - Tell the user what these rules leave open: they match a command's text, so a call written another way can slip past a deny; the allowed page writes can still tick Human Approved or change the Code row; and only these rules and the steps below keep the watch from launching a plan the user did not approve.
   Then tell the user the window, the approved runs in line, and the time of the morning report.
2. **No questions.** Inside the window, never ask the user anything, or wait for an answer or a prompt.
   - Where a step here or in vrl-run-experiment needs the user, as for an approval, a deviation, a failed Go on when, or a fix that changes the plan, leave that work, and record what they must decide, and why, for the morning report.
   - Launch only what the user approved. Never plan or approve an experiment; never change code, a config, a plan, or the SHA-256 in the Code row; never pass `--resume` or `--new-session`; never stop a process you did not start.
   - Append each launch, with its commit, and each restart, refusal, and skipped experiment to the night-watch log at once: it lists the processes the watch started.
3. **Each wake-up.** Read the time with `date`, and work out the running window, or else the last one and the next, with each end's date and UTC offset, such as `2026-10-08 22:00 +04:00`.
   - On a fixed interval, wake-ups can overlap: if the log's last `wake-up <time> started` line is under an hour old and no `wake-up <time> ended` line follows it, end the turn; otherwise append the started line, and the ended line when you end.
   - Once the window is under an hour away or running, create its log with its two ends if it is missing. Inside the window, do step 4; after it, do step 5 if the last window's log holds no report yet.
   - With `/loop`, end every wake-up by scheduling the next within an hour, or the loop ends: inside the window, soon after a run's next evaluation or end, else an hour later, and no later than the window's end; outside it, an hour later, or at the window's start if sooner. Stop the loop after the morning report. On a fixed interval, end the turn.
4. **Inside the window.**
   1. **Runs.** Check every run of the experiments with Status Running, as steps 4 and 5 of vrl-run-experiment do: update their pages, and close an experiment whose runs have all ended, leaving its analysis for the morning report. Restart, with `--restart`, only a run whose log has no footer and no live process, as after a node failure; a run that needs a fix stays stopped.
   2. **GPUs.** The GPUs on the `free:` line of `resources.sh --allowed <the GPU ids in docs/AGENTS/machine.md>` are free; with `free: unknown`, no `free:` line, or a failed call, none is. Record the reason, and every `note:` line, for the morning report. With a job scheduler, launch nothing.
   3. **Launch.** While a GPU is free, launch the next run in line, as steps 1, 3, and 4 of vrl-run-experiment do: first the waiting runs of Running experiments, oldest experiment first; then the runs of the next approved experiment, Status Planned and Human Approved checked, by its idea's Priority, then the earliest Created. Launch a run only if it passes the checks of those steps, and if every step before it, the smoke run included, is done or is itself a run; the tmux session exists or starts with its command; the idea's Budget limits allow it, counted as in vrl-plan-experiment step 1, with `gpu_hours.py`, which must not exit 3; and the storage for its outputs is not nearly full, by its quota command where `docs/AGENTS/machine.md` names one. Otherwise record why, and try the next run. If `launch_run.sh` exits with anything but 0, record its reason, and launch nothing more of that experiment. In remote mode, never sync: a run whose checkout's mirror holds another commit is refused, and waits for the user to sync.
5. **Morning report.** At the first wake-up after the window, stop launching; the runs keep going. Show the user the report, and append it to the night-watch log:
   - each run launched, finished, or restarted overnight, with its experiment, GPU, and outcome or progress;
   - each GPU's use, from `gpu_hours.py --json --since '<window start>' --until '<window end>'` on the logs folder, with dates and UTC offsets: a GPU of `docs/AGENTS/machine.md` missing from `by_gpu`, or with fewer hours than the window, sat idle for the rest, so say why, from the night-watch log; list any hours it could not count;
   - the runs still going, with their ETA: nothing watches them now, so the user picks them up with vrl-run-experiment;
   - what waits for the user, each with what they must decide: a skipped experiment, a run stopped for a fix, an approval to give, or a finished experiment to analyze.

## Rules

- At the start, run `bash <this skill's folder>/../vrl-init-workspace/scripts/check_update.sh`. If it reports a newer release, tell the user once per session, with its update command, and go on; update the skills only when asked.
- Work from the root of a vibe-research-loop workspace, which holds `AGENTS.md` and `docs/AGENTS/`, and follow its rules; elsewhere, tell the user and stop.
- If `docs/AGENTS/remote.md` exists, follow it: edit code, plans, and tests here and send them only as commits with `vrl_ssh.sh sync`, recording the pins and plan hashes it prints. Read logs and results with `vrl_ssh.sh read`, `run`, or `launch_run.sh --status`, and bring back with `vrl_ssh.sh fetch` only a figure to upload or a lock file to commit. Write plotting and analysis scripts on the remote host. Run no code here, not even a quick check.
- Never improvise what the scripts in `<this skill's folder>/../vrl-init-workspace/scripts/` do: `launch_run.sh` starts every long-running command, `resources.sh` reports resources and free GPUs, `gpu_hours.py` counts GPU hours, `vrl_ssh.sh` reaches the remote host. Read a script's `--help` only when you need an option that this skill or a rule file does not give. If one refuses or cannot count something (exit code 3), tell the user why; work around it by hand only where a rule file says how.
- If `docs/AGENTS/feishu.md` exists, the memory store is Feishu, not Notion: follow that file instead wherever this skill names Notion, `ntn`, a page, a database, or a property, and wherever a rule below makes sense only in Notion.
- Use the `ntn` CLI for Notion and look up its usage live: `ntn --help`, `ntn api ls`, `ntn api <path> -X <method> --spec`. Always run `ntn api ... < /dev/null`, or it waits on stdin.
- Take the IDs of the project page and databases from `docs/notion/ids.md`. If it is missing, find them by exact title with `ntn api v1/search`, reading every page of results, ask the user which project if several match, and record them there with the columns Object, Title in Notion, Page ID, Database ID, and Data source ID.
- Create each new page from its database's template file, never from a Notion template: `ideas.md`, `experiments.md`, `findings.md`, or `papers.md` in `<this skill's folder>/../vrl-init-workspace/references/guide/notion_guide/templates/`. Set the default properties from the file's header, and write each part of the body only when you fill it, at its place, by its italic instructions. A page holds only content: no instruction text, no `…` placeholder. Whenever an Ideas, Experiments, or Findings page goes to the user for review, rewrite its opening callout in place as its template says.
- A page whose headings differ from its template's comes from an older template: find each section by name, not number, and tell the user before writing to it.
- Write pages, template headings, labels, and table headers included, in the language the workspace's language rules set for them, or else the reply language, with property names and select and status options exactly as the database defines them.
- Write sentences a colleague can follow without decoding. State each fact once, where it belongs, and elsewhere point to its page and section, unless a template asks to repeat it. Give a reason only for a deviation, a control, an estimate, a ✘, or where a template asks. Common abbreviations such as w/o, ckpt, or lr are fine, but never string abbreviations and symbols together without words. Spell out at first use only those uncommon in the field or made up for this project.
- Keep each table cell to a value, a phrase, or one sentence. Put a cell's several points on separate lines within it (a `\n` in its rich text, since a cell cannot hold list blocks), starting with `1.`, `2.` when order matters and `•` otherwise. When a cell would run past three lines, move its content into a list right below the table, with a short pointer in the cell.
- The user marks text for review by coloring it or its background red, orange, or purple; other colors are not marks. Read a page before every write, with the colors of all its text, table cells included (each rich-text item's `annotations.color` and the block's `color`), and read it back after; merge the user's edits instead of overwriting them. Answer each mark, telling the user what you change and why. Red means wrong: fix it. Orange means not understood: explain it in plainer words and rewrite it so it needs no explanation. Purple means not acceptable: propose an alternative, and keep the text and mark until the user decides. Write rewritten text without the mark; leave unresolved marks in place.
- Add a figure by uploading its PNG with `ntn files create --filename <name>.png --content-type image/png < <file>` and inserting it as an image block right above its caption.
- Write times in the `TZ` of the workspace's `.env`: `YYYY-MM-DD HH:MM` in text, and `"time_zone": "<TZ>"` on date properties.
- Never make a Human-In-Loop decision: tick Human Approved, set Confirmed or Overturned, or change a Budget limit the user has set.
